# ПОС — Преподавательская оценка студентов

Домашнее задание №2 по КПО.

Консольное приложение для выставления оценок студентам по критериям и расчёта итогового результата.

## Что делает программа

В программе можно добавлять студентов, создавать критерии оценивания, выставлять и исправлять оценки, смотреть итоговые баллы и экспортировать их в CSV.

Также можно изменить имя студента, отменить оценку, добавить несколько критериев за один раз и посмотреть общую статистику успеваемости.

Всё работает через консольное меню. Данные хранятся в памяти во время работы программы. После завершения они не сохраняются; результаты можно выгрузить в файл `results.csv`.

Основные понятия предметной области:

- `Student` — студент;
- `Criterion` — критерий с названием, максимальным баллом и весом;
- `Rubricator` — набор критериев;
- `Evaluation` — оценка конкретного студента по конкретному критерию;
- `Score` — значение выставленного балла;
- итог — рассчитанный результат студента в процентах.

## Запуск

Для проекта нужны Java 21 и Maven.

Запуск консольного приложения из папки `POS`:

```bash
mvn compile exec:java
```

Запуск тестов:

```bash
mvn clean test
```

Сборка проекта с проверками:

```bash
mvn clean verify
```

## Работа с программой

После запуска появляется меню:

```text
=== ПОС: Преподавательская оценка студентов ===
1. Добавить студента
2. Список студентов
3. Добавить критерий
4. Список критериев
5. Выставить или исправить оценку
6. Оценки и итог студента
7. Экспорт итогов в CSV
8. Отменить оценку
9. Статистика по курсу
10. Изменить имя студента
11. Добавить набор критериев
0. Выход
```

Для критерия вводятся название, максимальный балл и вес. При выставлении оценки нужно выбрать студента и критерий, а затем указать балл.

Если оценка по критерию уже есть, новый балл заменяет прежний. Отмена оценки удаляет её из текущих результатов. При добавлении набора критериев сначала проверяются все введённые данные: если хотя бы один критерий некорректен, набор не добавляется.

Пункт `9` показывает количество студентов, средний, минимальный и максимальный итоговый балл. Пункт `7` создаёт файл `results.csv` с UUID, именами студентов и итогами в процентах.

Для выхода нужно ввести `0`.

## DDD и доменная модель

В проекте используется подход Domain-Driven Design. Названия доменных классов совпадают с понятиями предметной области — это наш **Ubiquitous Language**.

### Entity и Value Object

`Student`, `Criterion` и `Evaluation` — **Entity**. У каждой сущности есть уникальный UUID. Например, два студента с одинаковыми именами всё равно являются разными студентами.

`Score` — **Value Object**, реализованный как `record`. Он не имеет отдельного идентификатора, неизменяем и сравнивается по значению. Например, два объекта `new Score(8)` равны друг другу.

### Агрегаты и границы ответственности

`Rubricator` отвечает за свой набор критериев: добавляет их, не допускает повторения ID и позволяет получить существующий критерий.

`Student` отвечает за корректность имени и его изменение через `rename()`.

`Evaluation` представляет отдельный факт оценивания, связывает идентификатор студента с критерием и хранит балл. При изменении балла она проверяет допустимый диапазон. Создание оценки вынесено в `EvaluationFactory`, а существование студента перед выставлением проверяет `EvaluationService`.

Такие границы выбраны для небольшого консольного приложения: не нужно хранить все оценки прямо внутри `Student` или объединять все сущности в один большой объект.

### Инварианты

Доменная модель не позволяет нарушить основные правила:

- имя студента и название критерия не должны быть пустыми;
- максимальный балл критерия должен быть больше нуля;
- вес критерия должен быть больше нуля;
- балл должен находиться в диапазоне от `0` до `maxScore` включительно;
- оценку можно создать только по критерию из `Rubricator`;
- в рубрикаторе не может быть двух критериев с одним UUID;
- `InMemoryEvaluationRepository` не допускает две оценки одному студенту по одному критерию;
- `FinalScoreService` проверяет балл относительно максимума критерия из текущего рубрикатора;
- `FinalScoreService` не допускает смешивания оценок разных студентов.

При некорректном вводе пользователь видит сообщение об ошибке, а приложение продолжает работать.

### Repository и Domain Service

`StudentRepository` и `EvaluationRepository` — интерфейсы хранения. Они определены как выходные порты приложения. Конкретные реализации `InMemoryStudentRepository` и `InMemoryEvaluationRepository` находятся в инфраструктуре.

`FinalScoreService` — **Domain Service**. Расчёт итога не принадлежит одной оценке или одному студенту: для него нужны все критерии, их веса и оценки студента.

Основная формула:

```text
Итог (%) = 100 × Σ((балл / максимум критерия) × вес) / Σ(весов)
```

Результат округляется до двух знаков после запятой. По умолчанию отсутствующая оценка считается нулевой. Например, если за домашнее задание получено `8/10` с весом `2`, а за экзамен — `10/20` с весом `1`, итог составит `70.00%`.

Формула и правило для отсутствующих оценок — проектные решения: конкретный способ расчёта в условии не задан. Итог каждый раз вычисляется по текущим оценкам, а не хранится отдельным изменяемым полем.

## Архитектура

Используется **Ports and Adapters (Hexagonal Architecture)**. Код разделён на три основные части.

### domain

В `domain.model` находятся `Student`, `Criterion`, `Rubricator`, `Evaluation`, `Score`, `EvaluationFactory` и `RubricatorBuilder`.

В `domain.service` находятся `FinalScoreService` и стратегии расчёта.

Домен не зависит от консольного интерфейса, файлов и Guice.

### application

В `application.usecase` находятся сценарии работы со студентами, критериями, оценками, расчётом итогов, экспортом и статистикой.

В `application.port.out` находятся интерфейсы `StudentRepository`, `EvaluationRepository` и `ResultExporter`.

`PosFacade` предоставляет консольному интерфейсу одну точку доступа к сценариям. Прикладные сервисы обращаются к портам, а не к конкретным хранилищам или CSV-файлу.

### infrastructure

- `infrastructure.console` — `ConsoleApp`, обработка команд и ввод/вывод;
- `infrastructure.persistence` — репозитории в памяти;
- `infrastructure.export` — `CsvResultExporter`;
- `infrastructure.di` — `PosModule`, конфигурация Google Guice.

`Main` создаёт DI-контейнер и запускает приложение.

### Направление зависимостей

```text
Infrastructure --> Application --> Domain
             (реализует порты Application)

Main --> PosModule (сборка зависимостей)
```

Инфраструктура также использует доменные типы при реализации портов, но `Domain` ничего не знает о внешних слоях. Благодаря этому можно заменить способ хранения или интерфейс, не переписывая доменную логику.

## Паттерны GoF

### Порождающий — Builder

`RubricatorBuilder` находится в `domain.model` и используется в `RubricatorService`.

Он позволяет последовательно собрать несколько критериев, проверить их и только потом добавить весь набор в действующий рубрикатор. Это решает проблему частичного добавления: ошибка в последнем критерии не оставляет первые критерии набора в системе.

Также в проекте есть `EvaluationFactory` — простая фабрика для централизованного создания оценок с проверкой критерия и диапазона балла. Это **не классический GoF Factory Method**; основным порождающим паттерном GoF в проекте является Builder.

### Структурный — Facade

`PosFacade` находится в пакете `application`.

Без него `ConsoleApp` пришлось бы напрямую работать с несколькими сервисами и знать их зависимости. Facade предоставляет понятные операции для меню, а сами сценарии остаются в Application Layer.

### Поведенческий — Strategy

Интерфейс `FinalScoreStrategy` находится в `domain.service`. Есть две реализации:

- `AllCriteriaWeightedStrategy` — учитывает все критерии, включая ещё не оценённые;
- `GradedCriteriaWeightedStrategy` — учитывает только критерии с выставленными оценками.

`FinalScoreService` работает с интерфейсом стратегии, а не с конкретной формулой. Основная стратегия выбирается в `PosModule`. Это позволяет менять правила расчёта без переписывания доменного сервиса. В обычном запуске используется `AllCriteriaWeightedStrategy`.

## Dependency Injection

Для внедрения зависимостей используется **Google Guice 7.0.0**.

В `PosModule` настраивается создание репозиториев, рубрикатора, сервисов, фабрики и фасада. В `Main` создаётся контейнер, который получает `ConsoleApp` и запускает программу.

`StudentRepository`, `EvaluationRepository` и `Rubricator` имеют жизненный цикл **Singleton** в пределах одного запуска. Это нужно, чтобы все сценарии работали с одними и теми же студентами, критериями и оценками.

Остальные компоненты получают необходимые зависимости через конструкторы. Код приложения не запрашивает объекты у контейнера самостоятельно.

## Тесты

Тесты написаны на JUnit 5.

Проверяются:

- инварианты и изменение `Evaluation`;
- основной и альтернативный расчёт итога;
- сборка критериев через `RubricatorBuilder`;
- отмена и исправление оценок;
- переименование студента;
- статистика по курсу;
- сценарии работы консольного меню и экспорт CSV;
- создание зависимостей через Guice и общий экземпляр хранилищ.

## Пример работы

Создание студента и критерия:

```text
Выберите действие: 1
Имя студента: Иван
Студент добавлен: Иван

Выберите действие: 3
Название критерия: Экзамен
Максимальный балл: 10
Вес критерия: 1
Критерий добавлен: Экзамен
```

Выставление оценки и получение итога:

```text
Выберите действие: 5
1. Иван
Номер студента: 1
1. Экзамен | Максимум: 10 | Вес: 1
Номер критерия: 1
Балл: 7
Оценка успешно сохранена.

Выберите действие: 6
1. Иван
Номер студента: 1

Результаты студента: Иван
Экзамен: 7 / 10
Итоговый балл: 70.00%
```

После выбора пункта `7` программа создаёт `results.csv`, где будет строка с Иваном и итогом `70.00`.

Для завершения работы используется пункт `0`.
